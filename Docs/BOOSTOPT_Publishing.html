Publishing BOOSTOPT to PyPI

A runbook, in order. Everything runs from the repo root with .venv active; scratch artifacts go to ../tmp/. The companion documents are Packaging (closed-source compiled builds) and RELEASING.md (policy and tagging).

0Decide these first — they are not technical

DecisionStatusWhy it blocks
Licencedrafted, unreviewed The EULA in LICENSE has [DECIDE] and [JURISDICTION] placeholders and no legal review. Publishing binds you to it.
Source visibilityundecided A normal wheel ships 80 readable .py files, including engine/gate.py. If that is unacceptable, §5 is your path, not §3.
Repo visibilityGitHub, private A private repo makes every sidebar link on your PyPI page 404.

The name is free. https://pypi.org/simple/boostopt/ returned 404 on 2026-08-09, which for the simple index means unregistered. Re-check before uploading — names can be claimed at any time, and PyPI normalises boost-opt, boost_opt and BoostOpt to the same name.

1Accounts (one-time)

  1. Register at pypi.org and test.pypi.org — separate accounts; credentials do not carry over.
  2. Enable 2FA on both. It is mandatory for uploading. Save the recovery codes — losing 2FA on the account that owns your package name is a painful recovery.
  3. Get an upload credential — an API token (__token__ / pypi-…), or Trusted Publishing (preferred: GitHub Actions authenticates via OIDC, so no long-lived secret is stored anywhere).

Registering an account does not reserve the name. Only a successful upload does.

2Pre-flight

pytest -q                                 # expect 236 passed, 3 skipped
./check.sh                                # end-to-end engine self-check
pytest -q -m "not toolchain"              # 8s sanity loop
  • Suite green — a lone toolchain failure is usually the known flake; re-run before investigating
  • version bumped in pyproject.toml
  • LICENSE reviewed by counsel, placeholders resolved
  • Repository / Issues URLs resolve for a logged-out visitor
  • boostopt still free on PyPI

3Build the wheel

Wheel only. python -m build with no flags also produces a .tar.gz sdist — your entire source tree. Uploading it publishes everything, regardless of licence.

pip install build twine
python -m build --wheel -o ../tmp/dist && git checkout -- build/ && git clean -fdq build/
twine check ../tmp/dist/*

The git checkout -- build/ is not optional: build/ is tracked but stale, and building rewrites a dozen files with unrelated drift.

Inspect exactly what you are about to publish

python -c "
import zipfile, glob
z = zipfile.ZipFile(glob.glob('../tmp/dist/*.whl')[0]); n = z.namelist()
print('.py files   :', len([x for x in n if x.endswith('.py')]))
print('server leak :', [x for x in n if x.startswith('boostopt_server')] or 'none')"

Expect server leak: none — boostopt_server is the proprietary tier and must never ship. Guarded by tests/invariants/test_boundary.py.

4TestPyPI rehearsal

twine upload --repository testpypi ../tmp/dist/*

python -m venv ../tmp/verify
../tmp/verify/bin/pip install -i https://test.pypi.org/simple/ \
    --extra-index-url https://pypi.org/simple/ boostopt
../tmp/verify/bin/boostopt demo
../tmp/verify/bin/boostopt analyze --verify-setup

The --extra-index-url is needed because TestPyPI does not mirror libclang.

boostopt demo is the real test: it compiles, differential-tests, sanitises and benchmarks real C++ from a bare install. An import smoke test would not catch a missing asset.

5Closed-source release

§3 ships readable Python. If that is unacceptable, the wheel must be built from compiled extension modules — see Packaging for the verified Nuitka process. Three things are not yet built:

  1. Platform tagging. A wheel containing a .so must be tagged cp311-cp311-manylinux_2_17_x86_64, not py3-none-any, or pip installs a Linux binary on macOS and it fails at import.
  2. A build matrix. ~9–12 wheels per release (manylinux x86_64/aarch64, macOS x86_64/arm64, Windows × CPython 3.11/3.12/3.13). Use cibuildwheel, with Nuitka inside each job.
  3. No sdist, ever — it would ship the source you just compiled away.

Until that exists, §3 and §4 are a rehearsal, not a release.

6Publish

twine upload ../tmp/dist/*

python -m venv ../tmp/final
../tmp/final/bin/pip install boostopt
../tmp/final/bin/boostopt demo

This claims the name permanently. PyPI allows yanking a version but never reuses or releases a project name.

7Tag and announce

git tag -a v0.1.0 -m "BOOSTOPT v0.1.0"
git push --tags

Create a GitHub Release from the tag with the changelog, then update boostopt.com and install.sh if the install instructions changed. Finally: rm -rf ../tmp/dist ../tmp/verify ../tmp/final
